# チケットから Draft PR までの自動実装

## 使い方

この運用を含む PR を main へマージした後、リポジトリを開いた新しい Codex セッションで次のように指示します。

```text
チケット1を対応して
```

`AGENTS.md` が番号付きチケットをスキルへ振り分けます。手動で指定する場合は `$implement-ticket チケット1を対応して` でも構いません。プロジェクトの信頼設定や Docker / GitHub の認証は利用環境側で必要です。スキルはサンドボックスや承認設定を無効化しません。

チケット番号は [ローカルの一覧](tickets/README.md)にある固定 ID です。GitHub Issue / PR の番号とは別です。まずチケット1から進め、次のチケットは前提の PR を main に取り込んでから依頼します。

```bash
make ticket TICKET=1  # 対象チケットと依存関係をコンテナで表示
make ci              # カタログの整合性・スクリプトのテストも含む
```

## 自動で進める範囲

1. 対象・依存関係・既存 PR・作業ツリーを確認する。
2. 最新の main から `feat/ticket-001-<slug>` 形式のブランチを作る。途中の作業なら既存ブランチ / PR を再開する。
3. オーケストレーターが作業を分け、必要なワーカーを起動して統合する。
4. 受け入れ条件を実装し、関連する検証を Docker 内で行う。
5. 自身による差分レビューと、実装担当とは独立したレビューを行う。
6. 指摘を修正し、影響範囲の検証とレビューを繰り返す。
7. 実装記録を保存し、コミット・push・Draft PR 作成を行う。PR 本文はリポジトリのテンプレートを基に日本語で記載する。
8. 最終コミットの GitHub CI を確認し、失敗すれば修正して再検証する。

ゴールは「受け入れ条件・実行できる検証が通り、把握した未解決の問題がない Draft PR」です。欠陥が存在しないという数学的な保証はしません。現在はオーナー主導の趣味開発段階であり、オーナーが手動操作を「問題なし」と明示した場合は、報告された範囲の受け入れ証跡として扱います。ブラウザ、デバイス、時間、測定値など未提供の詳細はそのまま未記録とし、推測で補いません。

クロスブラウザ、長時間負荷、物理遅延、ホスティングやデプロイの詳細検証は、オーナーが公開準備を開始するまで任意です。オーナーが既存チケットの手動受け入れ範囲を明示的に変更した場合は、対象チケット・計画・報告を先行 PR で揃えます。自動テスト、現在の回帰、必須 CI は省略しません。

PR は Draft のまま渡します。レビュー承認、ready 化、マージ、デプロイはこのフローに含みません。main の保護ルールと必須 CI は維持します。

再開対象が人によって ready に変更された既存 PR の場合は、その状態を保持して報告します。新しい PR を重複作成することはありません。

## エージェントとコスト

| 役割                     | モデル / effort                          | 担当                                         |
| ------------------------ | ---------------------------------------- | -------------------------------------------- |
| オーケストレーター       | セッションでユーザーが選んだモデルを維持 | 契約・分割・統合・最終判断・Git / PR         |
| 局所的な実装ワーカー     | `gpt-6-luna` / `medium`                  | 仕様と期待結果が明確で影響の小さい修正       |
| 実績に応じた実装ワーカー | `gpt-5.6-terra` / `medium`               | 品質・所要時間・利用可能性で有利な作業       |
| 通常の実装ワーカー       | `gpt-6-sol` / `medium`                   | 仕様調査や複数モジュールの整合が必要な実装   |
| 実質的な独立レビュアー   | `gpt-6-sol` / `high`                     | 差分の不具合・漏れ・検証不足を読み取りで確認 |

作業名やファイル数だけでモデルを決めず、仕様の明確さ、原因調査の必要性、失敗時の影響で選びます。型エラー修正でも原因が不明なら Sol を使います。Luna の作業中に契約の不明点や広い影響が見つかったら、担当を止めて Sol または親が引き継ぎます。過去の同種作業の結果から Terra が適していれば `gpt-5.6-terra` を選べます。`.codex/config.toml` は親モデルを変更せず、未分類の子には Sol を設定します。Luna と Terra は対応する `.codex/agents/` の役割または明示的なモデル指定で選びます。

最大3子エージェント、通常は最大2実装ワーカー。処理が依存する箇所を無理に並列化しません。全履歴を複製せず、小さなタスクと必要なファイルだけを渡します。細かな修正は親が処理し、再レビューは既存の指摘と変更範囲に絞りつつ回帰も確認します。料金単価や節約率は環境によって異なるので保証しません。

ツールが明示的モデル指定を受け付ける場合はそれを使用します。指定できない場合はカスタムエージェントと既定値を使用します。利用不可なら、知らないモデル名を作ったり自動で高コストモデルへ上げたりせず、親で進めて理由を記録します。API のトークン単価だけで Codex の実作業コストを断定せず、代表的な作業で修正回数と総所要時間も比較します。

## 中断・再開

同じ指示は既存 PR / ブランチを検出して再開します。作業ツリーに別の変更があれば維持し、必要なら独立 worktree を作ります。認証・権限・前提チケットなど外部要因で止まる場合は、未完了箇所、試した検証、次の操作を実装記録または最終回答へ残します。

CI 待ちやモデル呼び出しを無限に繰り返す運用にはしません。同じ原因が修正を伴う3回の試行でも解消しないときは、原因を切り分け、必要な外部入力を具体的に示します。既知の問題を消したことにして完了扱いにはしません。

## 配置と検証

- [AGENTS.md](../AGENTS.md): 新しいセッション向けの短い入口。
- [implement-ticket スキル](../.agents/skills/implement-ticket/SKILL.md): 自動実装の手順。
- [PR テンプレート](../.github/pull_request_template.md): 日本語の PR 本文と検証証跡の共通構成。
- [.codex/config.toml](../.codex/config.toml): 子エージェントの既定値。
- [チケットカタログ](tickets/index.json): 固定 ID と依存関係。
- [実装記録](tickets/reports/README.md): 受け入れ条件・レビュー・検証の証跡。

カタログ検証は存在しない依存先・循環・重複・不正なパスを検出します。スキルや AGENTS.md は命令文なので、検証に加え独立エージェントで新規セッション相当のシナリオ確認を行います。
